# Matched physical ZRAM repeat-I/O pilot

Seven rounds of the same eight 512 KiB corpora and six codecs ran on the Lenovo Intel N100 using a new, non-swap 2 MiB ZRAM device. Corpus order and codec order within each corpus were randomized with seed 84220. For each trial, a warmup write was followed by ten timed whole-corpus direct-I/O rewrites and ten timed whole-corpus reads; the final read was verified against the input. The times cover all ten operations, including syscall, kernel compression or decompression and any SIMD state handling. Thread CPU time and `mm_stat` compressed and allocator bytes are retained. All 336 trials passed and the device was removed; active swap configuration matched before and after. The tiny repeated workload and one final verification per ten reads are limitations. The fixed-size transfers are not a representative swap trace, and the recorded allocator usage includes rounding and small-device effects.

For sparse words, median ten-write/read times were 3.018/1.878 ms for GHY bitdirect versus 7.098/3.035 ms for LZ4; the medians of same-round time changes were -57.9%/-39.3%. Median allocated bytes were 286,720 versus 524,288. For period127, bitdirect writes took 2.949 versus 2.116 ms (+42.1% paired median time), with 32,768 bytes allocated by both. For bash executable pages, bitdirect took 14.213/2.636 ms versus 13.303/2.654 ms (+5.1%/-2.3% paired time), while both had median 667,648 allocated bytes. The [tables](tables.md) include all codecs, corpora, CPU times, compressed and allocated bytes and paired changes. Changes in elapsed time are not throughput percentages. zstd had a median 43.941/11.758 ms for bash versus bitdirect's 14.213/2.636 ms, with 585,728 versus 667,648 allocated bytes. Seven observations are insufficient to establish an overall real-world winner.

The root process sampled CPU-package RAPL energy around each write and read batch, shown in the tables as mJ. These short intervals include unrelated package activity and counter update granularity; some readings are zero and surprising time/energy combinations occur, so they cannot support a reliable energy ranking. They are not whole-system or battery energy. Hardware cycles were not captured. The JSON `scope` string saying no energy is a stale label inherited from the previous script; the explicitly named package-energy fields are actual readings. Raw trial order, all readings, input hashes, source and the post-run frequency settings are retained. Frequency was dynamic, so older 800 MHz results are not directly comparable. No representative pressure, application responsiveness, long-duration stability, SIMD-path count or production-readiness claim follows.
