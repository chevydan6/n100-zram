# Persistent-browser physical LZ4 versus zstd pilot

Six randomized matched rounds compared the running stock LZ4 and zstd ZRAM algorithms on the physical Intel N100 (`7.2.11-n100-gzram-btf`), using a separate 192 MiB high-priority temporary ZRAM swap device while both existing swaps stayed active. A disposable user-session cgroup (`MemoryHigh=384M`, `MemoryMax=768M`, `MemorySwapMax=192M`, `TasksMax=512`) ran a 96 MiB synthetic working set and two long-lived headless Chromium instances using disposable profiles and generated local pages. Each page retained 12 MiB of JavaScript array data. Six rounds of actual GCC compilation, sampled memory-content checks and 12 browser DevTools interactions ran per trial, with two seconds' intentional idle time in each cycle. The interaction performs a local DOM mutation and title query, and measures client-to-browser response time; it is not a mouse/keyboard GUI test. All 12 trials passed, the temporary swap was deactivated and removed, and original swap settings were verified. The user accepted manual reset in case of a hang. The controller also recorded 10 ms scheduling-probe lateness, cgroup samples, fault counts and package energy.

An initial no-test-swap smoke check using a 320 MiB memory.high and larger working set timed out a GCC compilation under heavy pressure; its error is retained. This completed test raised memory.high to 384 MiB and reduced artificial working-set and JavaScript allocation, so it is not a stricter cgroup threshold than the previous pilot. It does exercise sustained browser pages and actual DOM interactions, with median sampled cgroup swap use around 151 MiB. Further increasing pressure would require separate stability and cleanup review.

[Tables](tables.md) give medians, ranges, and medians of same-round LZ4/zstd changes. LZ4 versus zstd had median workload 15.060 versus 15.387 s (-2.2% paired), browser interaction 1.176 versus 1.352 ms (-10.7%), compile latency 210.6 versus 225.1 ms (-6.7%), and package energy 43.49 versus 46.10 J (-4.6%). Workload time contains 12 seconds of intentional sleeps. Sampled peak device allocation was 57.5 versus 46.4 MiB (+27.3% paired); peak cgroup swap was 151.8 versus 151.1 MiB (+0.5%). The median interaction change crosses 10%, but only six short pairs, 12 interactions per trial, ranges overlapping materially, generated pages and a local debugging interface prevent a real-world acceptance claim. Per-trial p95 is based on only 12 observations and is not a reliable tail-latency distribution.

The test device's high priority is global and may receive other processes' pages; sampled allocation at 0.5-second intervals may miss peaks. CPU package energy includes idle time and background activity and is not whole-laptop energy or battery life. The controller scheduler probe is not GUI responsiveness. Generated headless pages, simplified synthetic memory contents, six pairs and no long-duration stability, hardware cycles or complete CPU-utilization accounting limit interpretation. The normal zstd setup remains the default. Raw randomized trial order, page verification, interaction timings, energy and samples are retained. There is no demonstrated basis to change the production configuration.
