# First experimental physical boot: failure and SELinux correction

The user requested a physical boot. The one-time GRUB entry booted `7.2.11-n100-gzram`; the user reported a crash. The machine subsequently returned to `7.2.11-200.fc44.x86_64`, with stock `[zstd]` ZRAM and both the hibernation swap file and ZRAM swap active. The saved GRUB entry remained the original kernel and `next_entry` was empty. No intentional retry was attempted.

The previous boot's journal shows a concrete installation error: the experimental module directory and files copied from the home directory carried SELinux `user_home_t` labels. SELinux denied module loading, including `lz4hc_compress`, and zram-generator reported that `modprobe zram` failed. The zram device and swap setup subsequently timed out. This was our installation mistake. The user later reported seeing a Ctrl+D prompt. The journal confirms that SELinux also denied loading the FAT module, `/boot/efi` failed to mount, `local-fs.target` failed, and systemd entered emergency mode. This explains the observed prompt; the retained journal does not show a kernel panic. The selected emergency-mode evidence is in `emergency-selected.log`.

While running the original kernel, `restorecon -RF` was applied **only** to `/usr/lib/modules/7.2.11-n100-gzram`; inspection afterward showed `modules_object_t`/`modules_dep_t` labels and the experimental ZRAM module's contents retained their build hash. The saved installer source now includes the same labeling step for any future use; its original pre-fix version remains in Git history. This corrects the identified label error but has not been validated by booting the experimental kernel again. No SELinux policy was disabled or weakened, no stock kernel or stock module files were modified, and no experimental compressor was activated on the running system.

Selected previous-boot journal evidence and the correction log are retained. The existing experimental boot entry remains separate and the normal kernel remains the default. A physical retry requires a deliberate reassessment of the crash report, module labels and recovery plan. VM success did not predict this physical failure and is not production-readiness evidence.

A further review found `systemd` reporting `bpf-restrict-fs: Failed to load BPF object: No such process` during the experimental boot; the same message was not found in the current stock boot journal. The experimental configuration deliberately disabled kernel BTF/debug information to reduce build cost, while the stock kernel enables BTF. That is a plausible issue to investigate, not a demonstrated cause of the message; affected systemd filesystem restrictions may not have been applied, so security equivalence to stock is not established. Earlier initramfs messages show `i2c_dev` was inserted and `msr` was built in, whereas later module discovery failed when the incorrectly labeled installed module tree was accessed. Selected records are in `additional-selected.log`. A future boot must verify systemd security features as well as correcting module labels.
