# GCC LTO userspace zstd screen

The running experimental kernel is built with GCC and `CONFIG_LTO_NONE=y`. This experiment does not alter it. Upstream userspace Zstandard 1.5.7 was built on the physical N100 with matched GCC `-O3 -fPIC -march=x86-64-v3 -fno-tree-vectorize` settings, adding `-flto=2` for the candidate. Compiled candidate C objects contain `.gnu.lto` sections and GCC linked the shared library; assembly objects do not participate in C LTO. Nine randomized rounds compared the complete userspace codecs over 26 corpora. Candidate and control frames were identical on all 3,328 checked pages, and candidate frames decoded with independently loaded system zstd; truncation, undersized output and canaries were checked. This is finite validation, not a full sanitizer or kernel correctness gate.

The first short run suggested improved compression on some inputs, but [two fresh confirmation sessions](../terra-zstd-n100-lto-confirm-001/findings.md) did not reproduce broad gains. These builds and timings cannot establish kernel ZRAM performance, SIMD state costs, energy or application benefit. The result is not a reason to rebuild or switch the kernel; raw data and build log are retained.
