# Physical ZRAM direct-I/O pilot

On the physical Intel N100 running `7.2.11-n100-gzram-btf`, a newly hot-added, non-swap 2 MiB ZRAM device processed eight retained 512 KiB corpora using direct block I/O, five observations for each of six algorithms in a globally shuffled order (seed 74219; 240 trials). Each trial reset the device, wrote one 128-page corpus, read it back and compared every byte. The reported write and read elapsed and calling-thread CPU times bracket the respective system calls; they include Python and block-I/O costs as well as kernel codec and SIMD state handling. The `mm_stat` compressed and actual allocator bytes are recorded before the read. Each trial is independent; rounding overhead is exaggerated at this small device occupancy. All data comparisons passed. The device was removed and active swap configuration was preserved. No stock swap compressor was changed.

The full [tables](tables.md) show medians, bytes and median per-round percentage changes against LZ4; rounds are labels for randomized individual observations, not adjacent or tightly controlled pairs. Five samples, changing CPU frequency, scheduler activity, fixed 512 KiB transfers, no warmup control and the arbitrary cross-round pairing limit inference. On sparse words, GHY bitdirect wrote in median 0.726 ms versus LZ4 1.877 ms (median paired time change -60.6%), read in 0.415 versus 0.806 ms (-45.9%), and used 274,432 versus 520,192 allocated bytes. These time reductions are not throughput percentages. On period127, bitdirect took 0.702 versus 0.445 ms to write (+57.7% paired time), with equal 32,768 allocated bytes; on bash executable pages it took 3.622 versus 3.369 ms (+11.0%) and allocated 667,648 versus 630,784 bytes. SIMD and hybrid tradeoffs appear in the table. zstd's bash median was 11.025 ms write, 2.763 ms read and 577,536 allocated bytes. These cases do not establish an overall winner or representative memory-pressure performance.

No package energy or hardware cycles were captured in this pilot, and no battery-life claim follows. The experiment is not an actual swap or application workload, and does not prove which SIMD branch ran. The frequency policy was 700–3400 MHz with powersave governor at the subsequent environment capture; earlier 800 MHz timings are not comparable. Raw per-trial records, input hashes, settings, test source, and environment are retained. The first attempt stopped on `EBUSY` while resetting the test device; the original error is preserved and the device was subsequently removed. The cause of the transient holder is unknown. The rerun added bounded EBUSY retry and completed; neither attempt changed the active swap configuration. Next, repeat with tighter pairing, more samples and energy/cycles where available, then evaluate representative bounded memory pressure and responsiveness before making any go/no-go claim.
