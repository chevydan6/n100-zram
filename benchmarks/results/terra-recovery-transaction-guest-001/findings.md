# Temporary panic-policy rollback prototype: guest deferred

The goal is to investigate temporary runtime recovery settings without editing GRUB, boot entries, persistent sysctl files, or stock ZRAM. `gzram/tools/guest-recovery-transaction.sh` is an explicitly guest-only prototype: it refuses to run without both an isolated-guest marker and the hypervisor CPU flag. It snapshots three guest panic-related sysctls, installs an exit/signal rollback, tests a normal setup or an injected partial failure, and reads the values back after restoration. `gzram/tools/vm-recovery-transaction.py` constructs a diskless, networkless exact-kernel guest, holds the existing exclusive lock, compares host stock ZRAM and sysctls before/after, and checks the guest's success, failure and rollback markers.

The host-refusal check returned `RECOVERY_GUEST_REFUSED` with status 3. A guest launch was attempted but stopped before creating a guest: available memory was approximately 1.6 GiB, below the existing 2 GiB preflight limit. The original traceback is in `deferred-run.log`. No guest result or rollback success is claimed; the normal and failure paths still need the planned VM test. The launcher and helper have not been used to change host policy.

This experiment covers three runtime values only. It does not arm an independent watchdog, prove reboot after a panic, test EFI pstore, guarantee rollback after SIGKILL or a kernel hang, validate a host implementation, or satisfy the native recovery gate. Guest-only results cannot demonstrate physical N100 hard-hang recovery. A host-capable design would need a separately reviewed implementation, durable recovery/restoration mechanism, and verified safeguards before any use.

## Retry after freeing memory

At the user's request and after their confirmation that work was saved, the Chromium browser was closed normally. Available memory rose to 2,505,968 KiB. A fresh diskless, networkless KVM guest then ran the exact `7.2.11-200.fc44.x86_64` kernel with two vCPUs and 256 MiB. The normal setup and the injected failure each produced exactly one restoration marker, and an independent guest snapshot matched the original three sysctls after each path. The guest and launcher reported `passed`; all recorded host ZRAM and sysctl values matched before and after. The earlier insufficient-memory attempt remains preserved. `guest-result.json` and the compressed serial log retain the source hashes and raw evidence.

This is a first transaction check, not a validated host recovery solution. In particular, the prototype does not exercise restoration after an uncatchable termination, machine reset or kernel hang; it does not verify actual panic reboot, watchdog operation, persistent logs or native device safety. It refuses host execution. No experimental host module was loaded and no host boot or swap settings were changed.
