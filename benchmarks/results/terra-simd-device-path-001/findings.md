# Guest-only ZRAM SIMD dispatch evidence

An instrumented copy of the previously tested namespaced ZRAM module was built for the exact running kernel. The copy adds once-per-module-load markers after exiting the SIMD/FPU critical section, and markers for scalar fallback. It was loaded only inside diskless guests. This instrumentation changes code and timing; it provides branch evidence, not performance or production-readiness evidence. Build inputs, hashes, commands and the modified dispatch source are retained.

With AVX2 hidden from the guest, two module-load passes each reached the scalar encoder and scalar decoder, and neither vector marker appeared. With AVX2 exposed, each pass reached both vector encoder and vector decoder; neither scalar marker appeared. Inspection of both serial logs places each marker within the corresponding `ghy-simd` device operation, rather than another compressor. Each guest passed the existing stock-plus-experimental device round trips across five algorithms and 26 corpora, CPU1 offline/online and pinned-I/O checks, stock-device data comparisons and unloading checks. A once marker proves that a branch ran at least once per module load; it does not count all requests or quantify FPU cost.

The first wrapper incorrectly looked for `console.log` after a successful AVX2-hidden guest; the actual file is `serial.log`. Its failure status and unmodified guest output are retained. The corrected wrapper rechecked hashes and fallback markers, then ran the AVX2-exposed guest and checked its markers. Both guest result records and raw serial logs are retained. No host experimental module was loaded; host setting preservation is recorded in the guest results.

This resolves the narrow device-path observation gap in the earlier coexistence gate. It does not prove native module coexistence safety, recovery from a hard hang, real ZRAM speed, energy, or memory-pressure responsiveness. Boot-menu recovery remains unverified, so physical kernel experiments remain gated.
