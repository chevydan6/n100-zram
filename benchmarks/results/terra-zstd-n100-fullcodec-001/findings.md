# N100 scalar zstd match counter: complete userspace codec

An opt-in patch applies the guarded 32-byte match-count idea from the [component experiment](../terra-zstd-matchcount-001/findings.md) to an isolated upstream Zstandard 1.5.7 build (tag commit `f8745da6ff1ad1e7bab384bd1f9d742439278e99`). The kernel source reports the same zstd version, and its unmodified match-count function matches the upstream function; userspace and kernel integration still differ. Candidate and untouched control were built separately with the same GCC `-O3 -fPIC -march=x86-64-v3 -fno-tree-vectorize` flags, with only the candidate macro enabled. The first control build failed because explicitly overriding CFLAGS omitted `-fPIC`; the failure and successful build logs are retained. No kernel code or active ZRAM settings were changed.

On the physical N100, four concurrent validation workers checked 1,024 pages across eight corpora. Candidate and control frames were byte-identical on those inputs. Each frame was decoded by candidate, control and the independently loaded system libzstd; truncated frames and insufficient output capacity returned errors and checked output canaries remained intact. This is finite input coverage, not a comprehensive malformed-frame or full-codec sanitizer test. The earlier match-count component passed ASan/UBSan and guard-page tests; that does not substitute for full-codec sanitizer coverage. The matched benchmark used nine randomized rounds, 1,024 calls per corpus/variant batch, shared contexts and Python/ctypes timing; CPU and wall time and output sizes are retained.

The [table](tables.md) shows no convincing broad gain: paired median compression change was approximately +0.1% on bash and libc executable pages, -3.1% on period127, +1.7% on sparse words, and +2.3% on clustered data. Decompression has no intentional change, so differences there are measurement or library-layout effects, not a demonstrated decoder improvement. These are userspace measurements with Python overhead and no package energy or cycles, not native kernel/ZRAM or application performance. The candidate is not promoted for kernel integration on this evidence. Next investigate a different whole-codec bottleneck or collect a real match-length profile before changing this hot loop; do not infer overall benefit from the earlier component microbenchmark.
