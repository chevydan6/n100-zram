# Signed kernel source RPM provenance check

The earlier exact-kernel guest integration used a locally preserved Fedora Koji source RPM whose integrity digests passed but whose publisher signature had not been verified. Inspection now confirms that particular RPM is unsigned: `rpm -Kv` reports header and payload digests, but no signature. Its SHA-256 is `5e7c2d81cd5fc54749e94917b6c2604c23c089dd0d277681e85e54d04bf6edc6`, matching the [guest integration manifest](../terra-simd-zram-001/manifest.json).

A separately downloaded [Fedora Koji signed copy](https://kojipkgs.fedoraproject.org/packages/kernel/7.2.11/200.fc44/data/signed/6d9f90a6/src/kernel-7.2.11-200.fc44.src.rpm) passed `rpm -Kv` signature and digest checks using the locally installed Fedora 44 key, fingerprint `36f612dcf27f7d1a48a835e4dbfcf71c6d9f90a6`. The signed RPM's SHA-256 is `08c2ba8240dd40bf2c52e36f62a71c05f8353cca5da762b2a6b914d0d09dd08d`. Their full `rpm2cpio` streams have the identical SHA-256 `c12fc1f8a74acd45402c9afc309fa0ed070bc7452399a861feb61ae21cbebd9a`. The installed `kernel-core-7.2.11-200.fc44.x86_64` RPM database entry names `kernel-7.2.11-200.fc44.src.rpm` as its source and records the same signing-key ID. Koji [stores signed headers separately from the original RPM](https://koji.readthedocs.io/en/latest/signing.html), so different package file hashes alone are expected and do not imply different payloads.

These checks establish that the preserved unsigned source RPM's extracted payload matches this verified signed copy, conditional on trust in the locally installed Fedora key and RPM verification. They do not prove a bit-for-bit reproducible build of the running kernel, the integrity of every subsequently prepared source file, correctness of experimental modifications, or native safety. The signed source RPM is preserved locally in `build/terra-signed-source-audit-001/`; the original is unchanged. Raw verification outputs are retained here. Nothing was installed, loaded, or changed in the boot or ZRAM configuration.

A subsequent check extracted the five components named in the integration manifest from the verified signed RPM and matched each recorded SHA-256. It then streamed the signed package's kernel archive and matched all 20 recorded ZRAM reference file hashes both to that archive and to the saved reference directory. `verify-reference.py` repeats the hash comparison after these components have been staged; it does not itself verify the RPM signature. The first extraction attempt failed because the cpio member names start with `./` and the supplied patterns omitted that prefix; it extracted no matching files. The corrected extraction passed. This closes the reference-file provenance gap, but does not verify the later experimental edits, the compiler output against the running kernel, or native safety.
